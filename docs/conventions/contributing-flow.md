# Contribution flow

How a change travels from a branch to a merged PR. [CONTRIBUTING.md](../../CONTRIBUTING.md)
covers setup and the human side; this file is the operational checklist.

## Branch and commits

- Branch off `develop`, never off `main`.
- Name the branch after the change type: `feat/…`, `fix/…`, `chore/…`, `docs/…`.
- [Conventional Commits](https://www.conventionalcommits.org) for every commit and for
  the PR title. CI validates the title, so `fix(player): stop reporting position 0`
  passes and `fixed the player` does not.
- One concern per PR. A drive by refactor inside a bug fix costs the reviewer the ability
  to tell which line caused what.

## Before you open the PR

Run the full gate and read its output:

```bash
bun run test    # typecheck + unit tests + lint + format + i18n keys + Expo Doctor
bun run check   # the read-only Biome pass CI runs as its own job
```

CI runs those commands as separate jobs rather than through `bun run test`, and its Expo
Doctor step is `continue-on-error`, so a doctor warning will not fail your PR.

Then check the change itself:

- Tests exist for the behaviour you changed. A bug fix starts with a test that fails on
  the reported behaviour and passes once the fix is in.
- New shared or tunable values live in `constants/`. See [constants.md](constants.md).
- New UI strings exist in `translations/en.json` and nowhere else. Every other catalogue
  is generated by Crowdin, so editing `fr.json` by hand gets overwritten. Reuse an
  existing key when one already says the same thing, and keep one key per full sentence
  rather than assembling sentences from fragments.
- Server hosted images import `Image` from `@/components/common/ServerImage`, not from
  `expo-image`. See [custom-headers.md](../custom-headers.md).
- Behaviour that is not purely visual reaches both phone and TV in the same PR. See
  [tv.md](tv.md).
- [CLAUDE.md](../../CLAUDE.md) still describes the code after your change. A new tab
  group, native module, provider or top-level directory belongs in it, and so does an SDK
  bump that dates the stack section. `CLAUDE.test.ts` catches three of those cases; the
  rest is on you.

## Writing the description

The template sections are not decoration. A reviewer reads the description first and
trusts it, so every sentence in it has to survive a look at the diff.

- **Description**: what changed and why, in terms of the observed problem. Name the file
  or function where the fault was.
- **Ticket**: `Fixes #123` when an issue exists. Search the tracker before deciding none
  does.
- **Screenshots**: any UI change ships before and after images, for iOS and Android both.
  A video is better than a screenshot for anything animated.
- **Checklist**: tick only what is true. "Verified that changes behave as expected for
  all platforms" left unticked on a PR that edits Swift and Kotlin tells the reviewer
  exactly where to look, which is the point.
- **Testing instructions**: numbered steps a reviewer can follow without asking you a
  question, including how to tell success from failure.

## Verification depth

The simulator and the emulator prove that the code path runs. They do not prove hardware
behaviour: volume buttons, the silent switch, background playback, real network loss,
Chromecast, TV remotes. Anything in that list needs a physical device before the
checklist box gets ticked.

For playback and reporting changes, the Jellyfin server log is the ground truth. Play the
scenario, then read what the server actually recorded rather than what the app believes
it sent.

## After you open the PR

- Wait for CI. Every job, not just the fast ones.
- A red job is a claim to investigate, not a reason to push again. Reproduce it locally
  on your branch head and on the merge result. If it fails on `develop` too, it is not
  yours, and saying so in the PR saves the next person the same detour.
- Wait for the CodeRabbit review and answer it. Its inline comments often keep the actual
  content after a collapsed `<details>` block, so read the whole comment body. When it
  asks for a regression test, the test is part of addressing the comment.
- Push fixes as their own commits. The repo squashes on merge, so the intermediate
  history costs the reviewer nothing and shows how the feedback was handled.

## Review expectations

A reviewer is expected to look at the whole PR, not only the changed lines:

- the diff, with enough surrounding code to judge it, plus the callers of what changed
- the description, with each claim checked against the code
- every comment thread, including the inline ones
- CI, job by job
- what the change leaves behind: a flag nobody sets any more, a doc comment that now
  describes the opposite of the code, a duplicated constant
- the tests: what was added, what is missing, what a bot asked for and did not get
